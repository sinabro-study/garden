### 4.2 집계 방식 비교: 백엔드 Batch vs Data Team 집계

| 구분     | 백엔드 Batch (Spring Batch 등) | Data Team 집계 (DW/ETL)     |
| ------ | -------------------------- | ------------------------- |
| 데이터 원천 | 운영 DB 원장 직접 조회             | DW 적재본 (CDC/ELT 이후)       |
| 정합성    | 트랜잭션 기반, 원천과 즉시 일치         | 적재 지연·유실 가능, 최종 일관성       |
| 지급 연동  | 동일 시스템 내 상태 관리·이체 연동 용이    | 지급 시스템과 별도 연동 계층 필요       |
| 도메인 로직 | 수수료·공제 로직을 코드로 단일 관리       | 계산 로직이 SQL/파이프라인으로 이원화 위험 |
| 스키마 변경 | 애플리케이션과 함께 배포·전파           | 파이프라인 별도 수정, 전파 지연 발생     |
| 대용량 성능 | 청크 처리, 운영 DB 부하 발생         | 분산 처리로 대용량 유리, 운영 DB 무부하  |
| 건별 추적  | 계산 근거 스냅샷 저장 용이            | 집계 중심, 건별 역추적 별도 설계 필요    |
| 재처리    | 회차·단계 단위 재실행 설계 용이         | 파이프라인 백필(Backfill)로 대응    |
| 소유권    | 백엔드 팀                      | 데이터 팀                     |

- 권장 구조
  - 지급 근거가 되는 확정 정산은 백엔드 Batch로 산출할 것 (트랜잭션 정합성·지급 연동·건별 추적 필수 요건 충족)
  - Data Team 집계는 검증용 크로스체크와 통계/BI 용도로 운영할 것
  - 두 집계 결과를 상호 대사하여 이중 검증 체계로 활용 (불일치 시 알림)
  - 수수료 등 도메인 로직의 원본은 백엔드 코드 단일 소유로 하고, 데이터 팀은 결과 대조만 수행할 것
