# 정산 시스템 예시 코드
- 기준 문서: [[정산 시스템 설계]]
- 기술 기준: Kotlin + Spring Boot / Spring Batch / JPA
- 목적: 설계 문서의 핵심 원칙(불변 원천, 멱등, 상태 CAS, 다층 방어)이 코드로 어떻게 표현되는지 예시 — 실제 구현 시 예외 처리·트랜잭션 경계 보강 필요

## 1. 코드 ↔ 설계 매핑

## 2. 정산 원천 — 불변 엔티티
```kotlin
@Entity
@Table(
    name = "settlement_source",
    uniqueConstraints = [UniqueConstraint(name = "uk_source_event_id", columnNames = ["event_id"])],
)
class SettlementSource(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    val id: Long = 0L,

    // Kafka 이벤트 고유 ID — 유니크 제약이 중복 소비의 최종 방어선
    @Column(name = "event_id", nullable = false, updatable = false)
    val eventId: String,

    @Column(nullable = false, updatable = false)
    val orderId: String,

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, updatable = false)
    val txType: TxType,

    // 취소/환불은 음수 금액의 별도 레코드로 적재 (원 레코드 수정 금지)
    @Column(nullable = false, updatable = false, precision = 15, scale = 0)
    val amount: BigDecimal,

    @Column(nullable = false, updatable = false)
    val settlementBaseDate: LocalDate,

    @Column(nullable = false, updatable = false)
    val occurredAt: LocalDateTime,
)

enum class TxType { PAYMENT, CANCEL, REFUND }
```
- 모든 컬럼 `updatable = false` — JPA 레벨에서도 불변 강제
- 금액은 `BigDecimal`(원 단위, scale 0) — Double/Float 금지 원칙의 코드 표현

## 3. 원천 수집기 — Kafka 소비 + 멱등 처리
```kotlin
@Component
class SettlementSourceCollector(
    private val sourceRepository: SettlementSourceRepository,
) {
    @KafkaListener(topics = ["commerce.payment-event"], groupId = "settlement-collector")
    @Transactional
    fun consume(event: PaymentEvent) {
        // 1차: 조회로 중복 차단 (릴레이는 at-least-once — 중복 발행 전제)
        if (sourceRepository.existsByEventId(event.eventId)) {
            return
        }
        try {
            sourceRepository.save(event.toSettlementSource())
        } catch (e: DataIntegrityViolationException) {
            // 2차: 동시 소비 레이스는 유니크 제약이 차단 — 중복이므로 정상 종료
            log.info { "duplicate event skipped: ${event.eventId}" }
        }
    }
}
```
- 멱등 2계층: 조회(빠른 경로) + 유니크 제약(레이스 방어) — 어느 쪽이 뚫려도 중복 적재 불가

## 4. 회차 상태 CAS — 이중 실행 방어의 핵심
```kotlin
interface SettlementRepository : JpaRepository<Settlement, Long> {
    @Modifying
    @Query(
        """
        update Settlement s
           set s.status = :next
         where s.id = :id
           and s.status = :expected
        """
    )
    fun compareAndSetStatus(id: Long, expected: SettlementStatus, next: SettlementStatus): Int
}
```
```kotlin
@Transactional
fun startAggregation(settlementId: Long) {
    val updated = settlementRepository.compareAndSetStatus(
        id = settlementId,
        expected = SettlementStatus.CREATED,
        next = SettlementStatus.AGGREGATING,
    )
    // 갱신 0건 = 다른 인스턴스가 이미 선점 — 락이 뚫려도 여기서 중단됨
    check(updated == 1) { "settlement $settlementId is already in progress" }
}
```
- ShedLock이 만료로 뚫려도 이 조건부 UPDATE는 DB 원자성으로 한쪽만 통과 — 정확성의 최종 보루
```kotlin
// settlement-domain — 상태 전이 규칙은 엔티티가 소유 (외부에서 status 임의 대입 금지)
@Entity
class Settlement(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    val id: Long = 0L,
    val targetId: Long,
    val periodFrom: LocalDate,
    val periodTo: LocalDate,
) {
    @Enumerated(EnumType.STRING)
    var status: SettlementStatus = SettlementStatus.CREATED
        protected set

    fun verify() {
        check(status == SettlementStatus.AGGREGATED) { "verify 불가 상태: $status" }
        status = SettlementStatus.VERIFIED
    }

    fun hold(reason: String) {
        check(status == SettlementStatus.AGGREGATED) { "hold 불가 상태: $status" }
        status = SettlementStatus.HOLD
        this.holdReason = reason
    }

    fun confirm() {
        check(status == SettlementStatus.VERIFIED) { "confirm 불가 상태: $status" }
        status = SettlementStatus.CONFIRMED
    }
}
```
- 이중 방어의 역할 분담: 엔티티 가드는 잘못된 전이(로직 오류)를, DB CAS는 동시 실행(경쟁 상태)을 각각 차단

```kotlin
// settlement-domain — 금액 값 객체: 반올림 규칙을 한 곳에 캡슐화
@JvmInline
value class Money(val amount: BigDecimal) : Comparable<Money> {
    init {
        require(amount.scale() <= 0) { "금액은 원 단위 정수만 허용: $amount" }
    }

    operator fun plus(other: Money): Money = Money(amount + other.amount)
    operator fun minus(other: Money): Money = Money(amount - other.amount)
    override fun compareTo(other: Money): Int = amount.compareTo(other.amount)

    // 요율 적용과 절사를 함께 캡슐화 — 반올림 규칙이 코드 전체에 흩어지지 않음
    fun applyRate(rate: BigDecimal): Money =
        Money(amount.multiply(rate).setScale(0, RoundingMode.DOWN))

    companion object {
        val ZERO = Money(BigDecimal.ZERO)
        fun won(value: Long): Money = Money(BigDecimal.valueOf(value))
    }
}
```
```kotlin
// settlement-domain — 요율 스냅샷이 스스로 수수료를 계산 (Tell, Don't Ask)
class FeePolicySnapshot(
    val feeRate: BigDecimal,
    val appliedAt: LocalDateTime,
) {
    fun feeFor(transactionAmount: Money): Money = transactionAmount.applyRate(feeRate)
}
```
```kotlin
// settlement-domain — 원천이 스스로 정산 상세를 만들어냄: 계산 주체는 도메인 객체
class SettlementSource( /* 2장과 동일 */ ) {
    fun settleWith(policy: FeePolicySnapshot): SettlementDetail {
        val transactionAmount = Money(amount)
        val platformFee = policy.feeFor(transactionAmount)
        return SettlementDetail(
            sourceId = id,
            amount = transactionAmount,
            platformFee = platformFee,
            appliedFeeRate = policy.feeRate, // 적용 요율 스냅샷 저장 (역추적 근거)
            payoutAmount = transactionAmount - platformFee,
        )
    }
}
```
```kotlin
// settlement-batch — 배치 Processor는 오케스트레이션만 (계산 로직 없음)
class SettlementItemProcessor(
    private val feePolicyProvider: FeePolicyProvider,
) : ItemProcessor<SettlementSource, SettlementDetail> {
    override fun process(source: SettlementSource): SettlementDetail {
        // 요율은 거래 발생 시점 스냅샷 사용 — 정산 시점 재조회 금지
        val policy = feePolicyProvider.snapshotAt(source.orderId, source.occurredAt)
        return source.settleWith(policy)
    }
}
```
- 객체 지향 원칙 적용 지점
  - `Money` 값 객체: 반올림(절사) 규칙을 단일 지점에 캡슐화 — "전 시스템 단일 규칙"의 코드적 강제
  - `FeePolicySnapshot.feeFor()`: 요율을 꺼내서(getter) 밖에서 곱하지 않고, 정책 객체에게 계산을 시킴
  - `SettlementSource.settleWith()`: 데이터와 그 데이터를 사용하는 계산이 같은 객체에 위치
  - 배치 Processor: 스냅샷 조회(인프라 의존)와 계산(순수 도메인)의 경계만 담당

## 6. 합계 검증 Step — 확정 차단 게이트
```kotlin
@Component
class VerifyAggregationTasklet(
    private val detailRepository: SettlementDetailRepository,
    private val settlementRepository: SettlementRepository,
) : Tasklet {
    override fun execute(contribution: StepContribution, chunkContext: ChunkContext): RepeatStatus {
        val settlementId = chunkContext.jobParameter<Long>("settlementId")
        val settlement = settlementRepository.findByIdOrNull(settlementId)
            ?: error("settlement not found: $settlementId")

        val detailSum = detailRepository.sumPayoutAmountBySettlementId(settlementId)
        if (detailSum != settlement.aggregatedAmount) {
            // 건별 합 ≠ 집계값 — 확정 진입 차단
            settlement.hold(reason = "AGGREGATION_MISMATCH detail=$detailSum aggregated=${settlement.aggregatedAmount}")
            return RepeatStatus.FINISHED
        }
        settlement.verify()
        return RepeatStatus.FINISHED
    }
}
```

## 7. 지급 모듈 — 멱등키와 타임아웃 처리
```kotlin
@Service
class PayoutService(
    private val payoutRepository: PayoutRepository,
    private val bankingClient: BankingClient,
    private val ledgerService: LedgerService,
) {
    @Transactional
    fun execute(settlementId: Long) {
        // idempotency_key 유니크 제약 — 동일 회차 중복 지급 원천 차단 (방어 최종 계층)
        val payout = payoutRepository.findBySettlementId(settlementId)
            ?: payoutRepository.save(Payout.create(settlementId))

        if (payout.isCompleted()) return

        try {
            val result = bankingClient.transfer(
                TransferRequest(
                    idempotencyKey = payout.idempotencyKey,
                    account = payout.account,
                    amount = payout.amount,
                )
            )
            complete(payout, result)
        } catch (e: BankingTimeoutException) {
            // 임의 재시도 금지 — 이체가 됐는지 모르는 상태에서 재요청하면 중복 이체
            val status = bankingClient.getTransferResult(payout.idempotencyKey)
            when (status) {
                TransferStatus.SUCCESS -> complete(payout, status.toResult())
                TransferStatus.FAILED -> payout.fail(status.resultCode)
                TransferStatus.UNKNOWN -> payout.markPendingCheck() // 별도 배치로 재조회
            }
        }
    }

    private fun complete(payout: Payout, result: TransferResult) {
        payout.complete(result)
        ledgerService.recordPayout(payout) // 지급 완료 분개
    }
}
```

## 8. 원장 분개 — 복식부기
```kotlin
@Service
class LedgerService(
    private val ledgerRepository: LedgerEntryRepository,
) {
    fun recordPayout(payout: Payout) {
        // 차변·대변 쌍 기록 — Append-only, UPDATE/DELETE 금지
        ledgerRepository.saveAll(
            listOf(
                LedgerEntry.debit(Account.UNSETTLED_PAYABLE, payout.amount, payout.id),  // 미정산금(부채) 감소
                LedgerEntry.credit(Account.CASH, payout.amount, payout.id),              // 현금(자산) 감소
            )
        )
    }
}
```
- 모든 분개는 차변 합 = 대변 합 — 잔액 대사 시 이 불변식으로 전체 자금 흐름 검증

### 9.1 Money — 반올림 경계값 (가장 촘촘해야 하는 영역)
```kotlin
class MoneyTest {
    @Test
    fun `요율 적용 시 원 단위 미만은 절사한다`() {
        val fee = Money.won(999).applyRate(BigDecimal("0.033"))
        // 999 × 0.033 = 32.967 → 32 (절사)
        assertThat(fee).isEqualTo(Money.won(32))
    }

    @Test
    fun `절사 경계값 - 소수점이 없는 경우 그대로 유지된다`() {
        val fee = Money.won(10_000).applyRate(BigDecimal("0.025"))
        assertThat(fee).isEqualTo(Money.won(250))
    }

    @Test
    fun `음수 금액(환불 원천)의 절사 방향을 검증한다`() {
        val fee = Money.won(-999).applyRate(BigDecimal("0.033"))
        // -32.967 → RoundingMode.DOWN은 0 방향 절사 → -32
        // 결제 시 부과한 수수료(32)와 환불 시 되돌리는 수수료가 일치하는지가 핵심 검증 포인트
        assertThat(fee).isEqualTo(Money.won(-32))
    }

    @Test
    fun `원 단위가 아닌 금액은 생성할 수 없다`() {
        assertThatThrownBy { Money(BigDecimal("100.5")) }
            .isInstanceOf(IllegalArgumentException::class.java)
    }
}
```

### 9.5 상태 CAS — 동시성 통합 테스트
```kotlin
@SpringBootTest
class SettlementConcurrencyTest {
    @Autowired lateinit var settlementRepository: SettlementRepository

    @Test
    fun `두 인스턴스가 동시에 집계를 시작해도 한쪽만 성공한다`() {
        val settlement = settlementRepository.save(settlementInStatus(SettlementStatus.CREATED))
        val executor = Executors.newFixedThreadPool(2)
        val successCount = AtomicInteger(0)

        val tasks = List(2) {
            Callable {
                val updated = settlementRepository.compareAndSetStatus(
                    settlement.id, SettlementStatus.CREATED, SettlementStatus.AGGREGATING,
                )
                if (updated == 1) successCount.incrementAndGet()
            }
        }
        executor.invokeAll(tasks)

        assertThat(successCount.get()).isEqualTo(1) // 정확히 한쪽만 선점
    }
}
```
- 테스트 우선순위: 반올림 경계값(9.1)과 합계 불변식(9.2)이 최우선 — 금액 오류는 가장 비싼 버그
- 9.5는 실제 DB(Testcontainers 등) 기반 통합 테스트로 실행할 것 — 인메모리 DB는 락 동작이 다를 수 있음
