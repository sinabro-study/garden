# 백엔드 기술 학습 계획

작성일 2026-11-15 · 출발점 기초 · 주 5시간 · 60주/300시간

## 일정과 목표

1~30주에는 Java → Spring → DB → Cache → Queue를 기초부터 심화까지 공부한다.
31~60주에는 같은 서비스를 분리하고 배포하고 운영하면서 분산 시스템·MSA·DevOps·SRE·Infra를 연결한다.
22주부터는 주차별로 개념, 실패를 포함한 실습, 검증 기준을 정한다. [22~60주차 상세 계획](#메시징과-운영-상세-계획)
주 5시간은 SAP 학습 계획의 운영 방식을 가져온 초기 기준이다. 4주마다 실습에 걸린 시간과 이해도를 보고 조정한다.

실습에서는 Java·Spring Boot로 상품 조회, 주문 생성, 재고 차감, 주문 확정 이벤트를 처리하는 모듈러 모놀리스를 단계적으로 만든다.
DB는 PostgreSQL, 캐시는 Redis를 기준으로 한다. 메시징은 RabbitMQ로 큐의 동작을 확인하고 Kafka로 파티션 로그와 리플레이를 비교한다. 두 브로커는 같은 주문 이벤트를 사용해 별도 실습으로 비교한다.
마지막에는 요청 흐름을 설명하고, 수치로 병목을 찾고, 장애 중에도 재고와 주문 상태가 올바르게 유지되는지 재현한다.

## Queue 이후 추천 순서

1. **분산 시스템 기초.** 원격 결제 호출이 타임아웃되면 결제가 반영됐는지 모를 수 있다. Queue에서 다룬 멱등성과 재시도를 원격 호출로 확장한 뒤 복제, 일관성, 파티셔닝을 공부한다. [AWS Builders’ Library의 타임아웃과 재시도](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)
2. **MSA.** 주문과 재고의 모듈 경계 및 데이터 소유권을 정하고 주문 확정 알림 워커 하나를 독립 서비스로 분리한다. 독립 배포의 이점과 원격 호출·계약 관리 비용을 실습 결과로 비교한다. [Martin Fowler의 Monolith First](https://martinfowler.com/bliki/MonolithFirst.html)
3. **DevOps.** 서비스 경계를 정한 뒤 테스트·이미지 빌드·배포·롤백을 반복 가능한 절차로 만든다. DB 변경이 있으면 애플리케이션 버전 간 호환성도 확인한다.
4. **SRE.** 주문 성공률과 지연 시간, 이벤트 처리 시간을 사용자 관점에서 재고 SLI와 SLO를 정한다. 대시보드와 알림을 보고 장애를 진단하고 복구한다. [Google SRE의 Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)
5. **Infra 심화.** 서비스의 자원 요구를 관찰한 뒤 컨테이너 제한, 로드밸런싱, 스토리지, 고가용성을 연결한다. Linux 프로세스·포트·DNS·HTTP와 Docker/Compose 기초는 앞쪽 실습에서 필요한 시점에 함께 익힌다. [Docker Compose 문서](https://docs.docker.com/compose/) · [Kubernetes 개념 문서](https://kubernetes.io/docs/concepts/)

## 메시징과 운영 상세 계획

매주 같은 주문 서비스를 사용한다. 결제와 알림은 로컬 모의 서비스로 실행한다.
값을 비교하는 실습에서는 입력 데이터, 요청 수·동시성, 장애를 넣은 시점, 변경 전후 결과를 함께 남긴다.
시간이 더 필요한 실습은 개념과 실행을 나누고 실제 측정 결과를 받은 회차에 진도를 갱신한다.

### 22~30주 · 메시징 정합성과 운영

#### 22주 · Dual write와 Transactional Outbox

- **학습** · 주문 DB 커밋과 브로커 발행을 두 작업으로 수행할 때 생기는 실패 구간을 찾는다. 주문 행과 Outbox 행을 같은 DB 트랜잭션에 쓰고 이벤트 ID·주문 ID·유형·본문을 정한다.
- **실습** · 단순 이중 쓰기에서 DB 커밋 직후 발행을 실패시킨다. Outbox 방식으로 바꾼 뒤 정상 커밋, 주문 처리 오류로 인한 롤백, 브로커 중단을 재현한다.
- **검증** · 커밋에는 주문과 Outbox가 모두 생기고, 롤백에는 둘 다 사라진다. 브로커 중단 중에 커밋된 이벤트가 DB에 발행 대기 상태로 남는지 조회한다.

#### 23주 · Outbox Relay와 발행 복구

- **학습** · 워커가 발행 대상을 가져가는 방법, 워커 사망 시 점유 해제, 브로커 확인 응답과 발행 완료 기록 사이의 실패 구간을 이해한다.
- **실습** · Relay 두 개를 실행한다. 발행 전 워커 종료와 브로커가 발행을 확인한 직후 워커 종료를 각각 만들어 이벤트 ID별 발행 시도를 기록한다.
- **검증** · 점유된 미발행 이벤트는 다시 처리되고, 이미 발행된 이벤트는 중복될 수 있음을 실행 기록으로 확인한다. 발행 실패를 완료 상태로 기록하는 경로가 있는지 테스트한다.

#### 24주 · CDC와 WAL 기반 이벤트 발행

- **학습** · PostgreSQL 변경을 WAL에서 읽는 과정과 복제 슬롯이 보존하는 위치를 살펴본다. polling relay와 CDC에서 지연, 중단 후 재개, 운영 부담의 차이를 비교한다.
- **실습** · 로컬 Debezium으로 Outbox 행을 Kafka 이벤트로 보내고 커넥터 중단 중 주문을 추가한다. 재시작 뒤 수신한 이벤트 ID와 복제 슬롯 위치를 기록한다.
- **검증** · 커넥터 재시작 후 커밋된 이벤트의 발행 여부를 확인한다. 장시간 중단 시 유지되는 WAL과 중복 가능성을 설명하고 해당 주문 서비스의 발행 방식을 고른다.

#### 25주 · 멱등 소비와 이벤트 순서

- **학습** · 처리한 이벤트 ID의 유일 제약과 비즈니스 갱신을 같은 DB 트랜잭션에 둔다. 같은 주문 안에서도 이벤트 전달 순서와 상태 전이 순서를 따로 고려한다.
- **실습** · 동일 이벤트를 두 소비자에 동시에 전달하고 DB 커밋 직후 ack 또는 오프셋 기록을 실패시킨다. 이벤트 버전 3을 2보다 먼저 보내 지연·재처리 정책을 검증한다.
- **검증** · 중복 재고 갱신이 없고 재처리 후 최종 주문 상태가 유효하다. 오래된 이벤트를 건너뛸 조건과 버전 공백을 보류해야 할 조건을 이벤트 의미에 따라 설명한다.

#### 26주 · Kafka 트랜잭션과 보장 범위

- **학습** · 동일 프로듀서의 재시도, Kafka 내부의 소비→처리→발행 트랜잭션, 외부 PostgreSQL 효과에 각각 어떤 보장이 필요한지 비교한다.
- **실습** · 입력 오프셋과 출력 레코드를 같은 Kafka 트랜잭션에 넣고 강제 중단한다. `read_committed` 소비 결과를 확인한 뒤 PostgreSQL 쓰기를 추가해 Kafka 트랜잭션 취소 시의 DB 상태를 비교한다.
- **검증** · 커밋·취소별로 출력 가시성, 오프셋 위치, DB 행 상태를 기록한다. 외부 효과를 한 번만 반영하기 위한 멱등 키 또는 DB 트랜잭션 전략을 설명한다.

#### 27주 · 재시도·DLQ·안전한 재처리

- **학습** · 일시적인 의존성 실패와 반복 실패하는 데이터 오류를 구분한다. 재시도 횟수·간격, DLQ에서 보존할 원본 이벤트 ID·실패 사유, 재처리 속도를 정한다.
- **실습** · 잠시 실패하는 소비자와 항상 거부되는 메시지를 각각 만든다. DLQ에서 실패 원인을 수정한 메시지를 소량씩 재투입하고 같은 메시지를 한 번 더 재투입한다.
- **검증** · 정상 메시지는 계속 처리되고 반복 실패 메시지는 정책에 따라 DLQ로 이동한다. 재투입 결과와 중복 차단을 기록하고 재처리를 멈출 조건을 정한다.

#### 28주 · 이벤트 계약과 스키마 진화

- **학습** · 이벤트 봉투와 본문의 역할, 필드 추가·삭제·타입 변경의 영향, 과거 이벤트를 다시 읽는 소비자의 요구를 살펴본다.
- **실습** · v1·v2 생산자와 소비자의 4가지 조합을 테스트한다. 선택 필드 추가와 필수 필드 타입 변경을 따로 적용하고 저장한 v1 이벤트를 v2 소비자에 다시 읽힌다.
- **검증** · 실패한 조합과 실패 이유가 테스트에서 드러난다. 호환 가능한 배포 순서, 과거 본문을 변환하는 지점, 오래된 계약 제거 조건을 제시한다.

#### 29주 · 메시지 적체와 처리량

- **학습** · 대기 건수, 소비자 lag, 가장 오래된 메시지 나이가 서로 다른 문제를 보여주는 이유를 이해한다. 유입률·처리율, 소비자 병렬성, 숨은 DB 병목을 연결한다.
- **실습** · 유입 속도를 유지하면서 소비를 늦춘다. 동일 부하에서 소비자 수 증가와 동시 처리량 제한을 각각 적용하고 한 주문 키에 요청을 집중시킨다.
- **검증** · 초당 처리량, 적체 해소 시간, 가장 밀린 파티션, DB 커넥션 대기를 함께 비교한다. 병렬성 추가의 효과가 사라지는 조건을 판단한다.

#### 30주 · Java~Queue 핵심 기술 통합

- **학습** · API 검증 → 주문 트랜잭션 → 재고 갱신 → Outbox → 소비의 흐름에서 DB·캐시·브로커가 맡은 보장을 정리한다.
- **실습** · 정상 주문, 동시 재고 차감, Redis 중단, Relay 중단, 동일 이벤트 재전달을 하나의 테스트 시나리오 묶음으로 실행한다.
- **검증** · 재고가 음수가 되지 않고 커밋한 주문의 이벤트가 복구 후 처리된다. 소비자 효과의 중복 여부를 DB로 대사하고 응답 지연·DB 조회·이벤트 처리 시간의 근거를 남긴다.

### 31~37주 · 분산 시스템

#### 31주 · 원격 호출과 부분 실패

- **학습** · DNS 조회, TCP 연결, TLS, HTTP 응답 단계와 각 단계에서 관측할 값을 연결한다. 연결·응답 타임아웃과 요청 전체 deadline의 경계를 이해한다.
- **실습** · 로컬 모의 결제에서 닫힌 포트, 늦은 응답, DB 커밋 후 응답 종료를 각각 재현한다. 클라이언트·서버 로그와 결제 테이블을 대조한다.
- **검증** · 호출자가 아는 결과와 서버의 실제 처리 결과를 구분하고 실패별 타임아웃 위치와 남은 처리 시간의 근거를 제시한다.

#### 32주 · 재시도 증폭과 장애 격리

- **학습** · 호출 계층별 재시도가 전체 호출량에 미치는 영향, 지수 backoff·jitter, 전체 deadline, circuit breaker와 bulkhead의 적용 지점을 공부한다.
- **실습** · 두 계층이 동시에 재시도하는 구성과 한 계층에 횟수·시간 한도를 둔 구성을 비교한다. 결제 모의 서버만 느려지게 만들고 상품 조회 응답도 관측한다.
- **검증** · 요청당 하위 호출 수, 오류율, p95, 스레드·풀 대기의 변화로 정책을 설명한다. circuit breaker가 열릴 때 클라이언트가 받는 결과를 확인한다.

#### 33주 · 멱등 API와 결과 대사

- **학습** · 호출자 범위의 멱등 키, 같은 키와 다른 본문의 충돌 처리, 진행 중·성공·실패 결과의 저장 위치와 결과 조회를 공부한다.
- **실습** · 동일 키 동시 요청, 같은 키의 본문 변경, 결제 커밋 후 응답 유실을 재현한다. 주문의 결제 상태를 결과 조회 또는 대사 작업으로 확정한다.
- **검증** · 같은 결제 의도에 대해 결제 기록이 1건이다. 충돌한 요청의 응답과 확정 결과를 보여주고 키 보존 기간을 재시도 기간과 연결한다.

#### 34주 · 복제와 읽기 일관성

- **학습** · 동기·비동기 복제, 쓰기 직후 읽기, 지연된 사본과 쿼럼을 공부한다. 네트워크가 분할된 동안 일관성과 가용성 선택이 어떤 요청에 영향을 주는지 설명한다.
- **실습** · 로컬 DB 복제본의 반영을 일시 정지한다. 쓰기 직후 기본 노드와 복제본을 읽고, 상품 목록과 주문 상세의 경로를 다르게 선택한다.
- **검증** · 복제본에서 읽기가 오래된 값을 돌려주는 조건을 관찰한다. 각 API가 감수할 수 있는 지연과 읽기가 기본 노드로 돌아가는 조건을 설명한다.

#### 35주 · 파티셔닝과 샤딩

- **학습** · 범위와 해시 분할, 키 편중, 교차 샤드 조회 비용과 데이터 재배치 시 읽기·쓰기 경로를 공부한다.
- **실습** · 특정 판매자에게 주문이 몰리는 데이터를 만들어 판매자 ID·주문 ID 기준으로 가상 샤드에 나눈다. 주문 상세와 판매자별 집계에 접근하는 샤드 수를 비교한다.
- **검증** · 샤드별 행 수·쓰기 비율과 교차 샤드 조회 비용을 근거로 키를 선택한다. 새 샤드 추가 시 조회 누락과 중복을 확인할 방법을 정한다.

#### 36주 · 리더 선출·합의·펜싱

- **학습** · Raft의 임기, 리더 선출, 로그 복제와 커밋을 따라간다. 이전 리더의 늦은 쓰기를 거절하는 펜싱 토큰의 필요 조건을 이해한다.
- **실습** · 3노드 타임라인에서 리더 단절과 2노드 단절을 각각 추적한다. 테스트 저장소에서는 새 토큰을 적용한 뒤 이전 작업자가 늦게 도착하는 쓰기를 실행한다.
- **검증** · 각 장애에서 선출과 커밋의 가능 여부를 설명한다. 보호 대상 저장소가 이전 토큰 쓰기를 거절하고 최신 토큰 쓰기를 허용함을 테스트로 확인한다.

#### 37주 · 분산 시스템 통합 점검

- **학습** · 결제의 불명확한 응답, 주문 읽기 지연, 재시도, 보상·대사 필요성을 하나의 요청 흐름에서 판단한다.
- **실습** · 결제 응답 유실과 주문 복제 지연을 겹친다. 주문 상태 근거, 재요청 결과, 대사 완료 시점을 타임라인에 놓는다.
- **검증** · 중복 결제 여부와 사용자에게 보일 상태를 데이터로 검증한다. 일관성 요구, 대기 가능 시간, 장애 복구 경로를 설계 결정에 남긴다.

### 38~43주 · MSA

#### 38주 · MSA 경계와 데이터 소유권

- **학습** · 도메인 상태, 같이 변경되는 코드·데이터, 호출 방향, 강한 일관성이 필요한 규칙을 기준으로 모듈을 나눈다.
- **실습** · 주문·재고·결제·알림의 변경과 읽기 의존성을 그린다. 알림 분리와 재고 분리를 각각 가정해 변경 시나리오 두 가지를 검토한다.
- **검증** · 모듈별로 어느 DB 상태를 변경할 수 있는지, 독립 배포로 얻는 이점과 분산된 상태를 맞추는 비용을 함께 설명한다.

#### 39주 · 알림 서비스 분리와 전환

- **학습** · 첫 분리 대상의 선택, 기존 경로와 새 경로의 공존, 관찰용 소비와 실제 알림 효과가 일어나는 소비를 구분한다.
- **실습** · 알림 워커를 별도 프로세스로 실행한다. 관찰 모드로 결과를 비교한 뒤 실습 플래그로 전환하고 새 워커를 중단한다.
- **검증** · 알림 서비스 장애 중에도 주문이 접수된다. 재기동 후 대기 알림이 처리되고 전환 및 복귀에서 같은 알림 의도가 중복 반영되지 않는다.

#### 40주 · 서비스 API 계약과 데이터 이전

- **학습** · API 응답·오류 계약, 소비자 계약 테스트, backfill과 이후 변경 따라잡기, 권위 데이터의 전환·복귀 지점을 정한다.
- **실습** · 이전·신규 알림 조회 API를 소비자 테스트로 비교한다. 조회 이력을 backfill한 뒤 새 레코드까지 맞추고 읽기 경로를 전환한다.
- **검증** · 데이터 건수·상태 대사와 신·구 소비자 테스트를 통과한다. 읽기 전환 이후의 쓰기 책임과 되돌릴 때 확인할 상태를 기록한다.

#### 41주 · Saga 상태와 보상 트랜잭션

- **학습** · 서비스별 로컬 커밋, 장기 작업 상태, 오케스트레이션·코레오그래피의 장애 추적 비용, 보상 동작의 비즈니스 의미를 살펴본다.
- **실습** · 재고 예약 → 결제 → 주문 확정으로 상태 전이를 구성한다. 재고 부족, 결제 거부, 결제 이후 확정 오류를 각각 재현한다.
- **검증** · 실패별로 종료 상태, 재시도할 단계, 예약 해제·환불 등 보상 조건을 표로 확인한다. 이미 완료된 단계에 대한 재요청도 검증한다.

#### 42주 · 분산 워크플로 복구와 대사

- **학습** · 단계 제한 시간, 보상 응답 유실, 자동 재시도 중단 조건, 수동 조정과 감사 이력이 필요한 상태를 공부한다.
- **실습** · 환불 기록이 커밋된 직후 응답을 유실시키고 Saga 실행 프로세스를 재시작한다. 단계 상태와 모의 결제 원장을 대조해 결과를 확정한다.
- **검증** · 중복 환불·중복 재고 복원이 발생하지 않는다. 복구되지 않은 작업을 목록에서 확인하고 어떤 정보로 담당자가 조정할지 기록한다.

#### 43주 · MSA 테스트와 설계 점검

- **학습** · 모듈 테스트, API·이벤트 계약 테스트, 실제 의존성을 사용하는 통합 테스트의 검증 범위를 정한다.
- **실습** · 알림 계약을 깨는 변경, 워커 중단, Saga 중복 요청을 각각 재현한다. 상관관계 ID로 HTTP 요청과 후속 이벤트 기록을 모은다.
- **검증** · 각 장애를 가장 일찍 발견하는 테스트와 발견하지 못하는 케이스를 제시한다. 알림 분리의 독립 배포 효과와 재고·결제 분리 비용을 다시 평가한다.

### 44~48주 · DevOps

#### 44주 · CI와 재현 가능한 빌드

- **학습** · Wrapper, 의존성 버전, 단위·통합·계약 테스트 실행, 실패 시 릴리스 차단, 산출물 식별을 공부한다.
- **실습** · 깨끗한 작업 환경에서 테스트와 패키징을 실행하는 CI 단계를 만든다. 트랜잭션 테스트와 계약 테스트가 깨지는 변경을 넣어 실패를 관찰한다.
- **검증** · 성공할 때만 커밋으로 추적 가능한 아티팩트가 생긴다. 로컬과 CI의 결과 차이가 나면 JDK·설정·DB 버전의 근거로 좁힌다.

#### 45주 · 컨테이너 이미지·설정·시크릿

- **학습** · 이미지 빌드 단계, 태그와 digest, 실행 사용자, 환경별 설정 주입, 시크릿의 참조 위치와 로그 노출을 공부한다.
- **실습** · 동일 이미지 digest로 두 환경 설정을 적용한다. 비밀 값 대신 임시 테스트 값을 주입하고 이미지 이력·컨테이너 로그·설정 파일 노출을 확인한다.
- **검증** · 서비스 환경을 바꿔도 이미지가 동일하고 시크릿 값이 이미지에 들어가지 않는다. 시크릿을 바꾸면 새 값을 읽는 시점과 재시작 여부를 확인한다.

#### 46주 · CD와 점진 배포

- **학습** · rolling·blue-green·canary의 트래픽과 용량 차이, 준비 상태 확인, 배포 전후 비교 지표와 중단 기준을 정한다.
- **실습** · 로컬 프록시나 배포 환경에서 구·신 버전을 동시에 실행한다. 소량 트래픽을 신버전에 보낸 뒤 성공률·지연을 비교하고 오류를 주입해 전환을 멈춘다.
- **검증** · 버전별 요청 수와 오류 관측값으로 배포 계속 또는 중단을 판단한다. 기존 버전으로 트래픽을 돌렸을 때의 요청 성공을 확인한다.

#### 47주 · 호환되는 DB 마이그레이션

- **학습** · 컬럼 변경의 expand → backfill → 전환 → contract, 장시간 잠금, 배치 재개, 애플리케이션과 DB의 롤백 가능 지점을 공부한다.
- **실습** · v1·v2가 공존하는 주문 테이블에 새 필드를 추가한다. backfill을 중간에 중단하고 재시작한 뒤 읽기·쓰기 경로를 바꾼다.
- **검증** · 신·구 버전과 단계별 스키마의 호환성을 테스트한다. 잔여 미변환 건수, 잠금 대기, 복귀 시 필요한 조치를 기록한다.

#### 48주 · 배포·롤백 통합 훈련

- **학습** · 빌드 산출물 식별 → 배포 → smoke test → 실패 판정 → 이미지·DB 복구의 책임과 순서를 연결한다.
- **실습** · 정상 릴리스와 오류 릴리스를 연속 실행한다. 두 번째 릴리스는 호환되는 스키마 변경을 포함하고, 판정 기준에 따라 이전 이미지로 돌아간다.
- **검증** · 어느 커밋과 이미지가 언제 배포됐는지 재구성한다. 롤백 후 주문 조회·생성, 변경 스키마, 이벤트 처리의 정상 여부와 소요 시간을 확인한다.

### 49~52주 · SRE

#### 49주 · 관측성 계측

- **학습** · 로그, 메트릭, 트레이스의 질문을 구분하고 요청 ID·이벤트 ID·trace context의 전달과 메트릭 레이블 카디널리티를 이해한다.
- **실습** · OpenTelemetry 계측을 추가하고 주문 HTTP 요청과 후속 이벤트를 연결한다. DB 느린 쿼리와 느린 소비자를 각각 넣는다.
- **검증** · 트레이스·메트릭·로그에서 두 지연의 발생 위치를 찾아낸다. 주문 ID를 메트릭 레이블 대신 조회 가능한 로그나 트레이스에서 찾는 경로를 보여준다.

#### 50주 · SLI·SLO와 오류 예산

- **학습** · 주문 성공률, 정해진 시간 안에 응답한 주문의 비율, 이벤트 처리 신선도의 분자·분모·측정 기간을 정한다.
- **실습** · 잘못된 사용자 입력, 서버 오류, 느린 성공, 이벤트 처리 지연이 섞인 데이터로 각 SLI와 오류 예산 소모를 계산한다.
- **검증** · 제외하는 요청과 포함하는 실패를 사용자 경험으로 설명한다. 같은 기간의 총 위반량과 급격한 소모 사례를 구분한다.

#### 51주 · 알림·장애 대응·회고

- **학습** · 오류 예산의 burn rate, 긴 창·짧은 창의 기준, 즉시 대응과 후속 작업의 판단, 런북과 회고의 작성법을 공부한다.
- **실습** · 짧고 큰 장애와 느리게 누적되는 장애를 재현해 알림 결과를 비교한다. 런북에 따라 완화하고 탐지·판단·복구 시간을 남긴다.
- **검증** · 알림이 사용자 영향과 연결되고 대응자가 첫 작업을 선택할 수 있다. 회고에 재발을 줄이는 구체적인 검증 항목을 추가한다.

#### 52주 · 부하 테스트와 용량 계획

- **학습** · 동시성, 처리량, 꼬리 지연, 포화 지점, 다운스트림 한계와 대기열 증가의 관계를 공부한다.
- **실습** · 워밍업 이후 부하를 단계적으로 높인다. DB 풀과 소비 동시성 중 한 항목을 바꾸고 유입 제한을 적용한 경우도 비교한다.
- **검증** · SLO를 유지한 최대 실측 부하와 처음 포화된 자원을 제시한다. 대기열 나이, p95, 오류율로 용량 여유와 유입 제한 정책을 설명한다.

### 53~60주 · Infra와 최종 통합

#### 53주 · Linux와 컨테이너 자원

- **학습** · 프로세스·스레드, 파일 디스크립터, 네임스페이스, cgroups, CPU throttling, 메모리 제한과 JVM 힙의 관계를 공부한다.
- **실습** · CPU와 메모리 제한을 각각 낮춘다. 프로세스 종료 상태와 컨테이너 자원 지표, GC·요청 지연을 비교한다.
- **검증** · 느려진 경우와 종료된 경우의 근거를 구분하고 제한 값, JVM 설정, 작업량 중 조정할 대상을 설명한다.

#### 54주 · 네트워크·로드밸런서·헬스 체크

- **학습** · DNS 캐시, TCP 연결, TLS 종료 지점, 프록시 연결, 헬스 체크, 연결 드레이닝을 요청 경로에 표시한다.
- **실습** · 프록시 뒤에 애플리케이션 두 개를 실행한다. 하나를 준비 실패 상태로 만들고, 진행 중 요청이 있는 상태에서 프로세스를 정상 종료한다.
- **검증** · 실패 요청이 어느 구간에서 생겼는지 로그로 찾는다. 새 요청 제외 시점과 기존 요청 완료 시점, 설정한 타임아웃을 비교한다.

#### 55주 · Kubernetes 워크로드와 배포

- **학습** · Pod·Deployment·Service, readiness·liveness·startup probe, 롤링 교체 도중의 서비스 엔드포인트 변화를 공부한다.
- **실습** · 로컬 클러스터에 API를 배포한 뒤 Pod 삭제와 준비가 늦는 이미지의 롤링 업데이트를 각각 실행한다.
- **검증** · Pod 상태와 서비스 엔드포인트, 클라이언트 성공률을 같은 시간축에 둔다. 각 probe가 어떤 조건에서 트래픽·재시작에 영향을 주는지 설명한다.

#### 56주 · Kubernetes 스케줄링과 확장

- **학습** · requests와 limits, 스케줄 가능한 용량, HPA 관측 지연, 확장된 애플리케이션이 DB·브로커에 거는 부하를 공부한다.
- **실습** · 로컬 클러스터에 단계 부하를 넣어 HPA 확장을 관찰한다. 높은 CPU 요청 때문에 새 Pod가 대기하는 경우와 DB가 포화된 경우를 비교한다.
- **검증** · Pod 수 증가와 실제 처리량 증가를 별도로 측정한다. 스케줄 지연, 연결 풀, 처리율 중 확장을 제한한 근거를 제시한다.

#### 57주 · 스토리지·백업·재해 복구

- **학습** · 컨테이너 볼륨과 DB 백업의 역할, WAL과 시점 복구, RTO·RPO를 실제 복구 절차의 측정 기준으로 연결한다.
- **실습** · 주문 데이터의 백업과 WAL을 준비하고 일부 실습 데이터를 삭제한다. 별도 DB에 삭제 직전 시점으로 복원하고 주문·Outbox·처리 내역을 대사한다.
- **검증** · 장애부터 재개까지 걸린 시간과 복구한 데이터 시점을 기록한다. 복원된 DB를 다시 연결할 때 미처리·중복 이벤트를 판별할 방법을 확인한다.

#### 58주 · IaC와 AWS 운영 설계

- **학습** · Terraform 구성·상태·plan·drift, AWS 네트워크와 실행 계층, 관리형 DB·캐시·브로커의 책임과 장애 범위를 연결한다.
- **실습** · 로컬 실습 리소스로 Terraform의 생성·변경 계획·drift를 관찰한다. SAP 학습 내용을 활용해 VPC·로드밸런서·컴퓨팅·DB·메시징의 AWS 배치와 데이터 경로를 설계한다.
- **검증** · 계획 출력으로 예상 변경을 설명하고, AWS 설계도에 요청·데이터 경로, 장애 격리, 비용 요인과 복구 경로를 표시한다.

#### 59주 · 복합 장애 훈련

- **학습** · 장애를 넣기 전 정상 기준, 피해 범위, 종료 조건과 복구 후 확인할 서비스·데이터 지표를 정한다.
- **실습** · 캐시 연쇄 만료와 DB 풀 포화, 브로커 중단과 Outbox 적체를 각각 로컬에서 재현한다. 지표에 따라 완화하고 유입·재처리 속도를 제어한다.
- **검증** · 완화 전후의 성공률·지연·적체·재고·주문 상태를 대조한다. 복구 후 남은 Outbox와 중복 효과를 확인하고 런북에 누락된 대응을 추가한다.

#### 60주 · 최종 백엔드 설계 평가

- **학습** · 주문 부하 증가와 처리 시간 요구가 새로 들어왔을 때 DB·캐시·Queue·서비스 경계·배포 환경을 다시 판단한다.
- **실습** · 예상 트래픽과 SLO를 정하고 설계 선택 하나를 반영한다. 59주와 다른 실패인 신버전 계약 오류 또는 결제 결과 불명확 상태를 재현하고 복구한다.
- **검증** · 설계 보고서에 데이터 흐름, 불변식, 대안의 비용, SLO 측정, 배포·복구 절차, 재현 방법을 담는다. 다른 사람이 같은 조건에서 주문과 이벤트 상태를 확인할 수 있다.

## 실습 방식

첫 수업은 작은 Java 예제로 진행한다. 프로젝트 시작 시 호환되는 LTS JDK와 Spring Boot 조합을 공식 문서에서 확인하고 실습에 쓴 버전을 기록한다.
로컬에서 애플리케이션과 임시 실습 데이터를 사용한다. PostgreSQL부터 필요한 의존 서비스를 Compose로 붙인다. DNS·포트·네트워크·프로세스 개념은 문제가 발생하는 곳에서 함께 확인한다.
실습 결과에는 입력 데이터와 부하 조건, 정상·실패 시 실제 관측값, 복구 후 재검증 결과를 남긴다. 코드 작성 없이 설계로 진행했다면 진도에 설계 근거를 기록한다.
DB 트랜잭션은 기존 [Transaction 완전 정복](../Transaction%20완전%20정복/(Summary)%20Transaction%20완전정복.md)의 ACID·격리·전파·로그·잠금 노트와 연결한다. AWS 비교 실습은 기존 SAP의 RDS·ElastiCache·SQS·컨테이너 수업에서 익힌 개념을 활용한다.
