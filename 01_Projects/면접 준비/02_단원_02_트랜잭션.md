# 02. Spring 트랜잭션과 MyBatis·JPA 혼용

## 기술 개념 전체 설명

### 트랜잭션 경계

트랜잭션은 여러 DB 변경을 하나의 확정 또는 취소 단위로 묶는다. Spring의 @Transactional은 보통 프록시가 메서드 진입·종료에서 begin, commit, rollback을 제어한다. 같은 객체 내부 호출은 프록시를 거치지 않을 수 있다.

트랜잭션은 **어떤 작업들이 함께 성공하거나 함께 실패할지**를 정한다. ACID는 원자성(전부 확정 또는 취소), 일관성(정의한 제약 유지), 격리성(동시 트랜잭션 간 간섭 제어), 지속성(commit된 결과 유지)을 뜻한다. 일관성이란 DB가 모든 업무 규칙을 자동으로 알아서 보장한다는 의미가 아니다. 재고 음수 방지처럼 애플리케이션에서 정의하고 검사해야 하는 규칙도 있다.

`@Transactional`은 보통 Spring 프록시를 통과할 때 적용된다. 프록시가 트랜잭션 매니저에 시작을 요청하고, 메서드가 정상 종료되면 commit을, 롤백 대상 예외가 나면 rollback을 요청한다. **프록시가 직접 `flush()`를 호출한다는 뜻은 아니다.** JPA가 commit 과정에서 변경을 flush할 수 있다.

```mermaid
sequenceDiagram
 participant C as 호출자
 participant P as Spring 트랜잭션 프록시
 participant TM as JpaTransactionManager
 participant EM as 실제 EntityManager
 participant DB as Database
 C->>P: @Transactional 메서드 호출
 P->>TM: 트랜잭션 시작 요청
 TM->>EM: 생성·현재 스레드에 바인딩
 EM->>DB: begin / 연결 참여
 P->>EM: 서비스의 JPA 작업
 P->>TM: 정상 종료: commit 요청
 TM->>EM: JPA 트랜잭션 commit
 EM->>DB: 필요 시 flush SQL 후 COMMIT
 TM->>EM: 바인딩 해제·종료
 P-->>C: 결과 반환
```

실제 `EntityManager`는 새 물리 트랜잭션에 연결된다. `@PersistenceContext`로 주입한 공유 프록시는 현재 트랜잭션의 실제 `EntityManager`에 호출을 전달한다. 같은 물리 트랜잭션이면 영속성 컨텍스트도 공유한다.

### 전파와 롤백

REQUIRED는 기존 트랜잭션에 참여하고 REQUIRES_NEW는 독립 트랜잭션을 만든다. 기본적으로 RuntimeException과 Error에서 롤백하지만 checked exception은 설정을 확인해야 한다. 독립 트랜잭션은 추가 커넥션 점유와 외부 트랜잭션과의 확정 시점 차이를 만든다.

| 전파 옵션 | 외부 트랜잭션이 있을 때 | 주요 결과 |
| --- | --- | --- |
| `REQUIRED` | 같은 물리 트랜잭션에 참여 | 내부 작업만 별도로 commit할 수 없음. 내부에서 rollback-only가 되면 외부 commit도 실패할 수 있음 |
| `REQUIRES_NEW` | 외부 트랜잭션·자원을 잠시 중단하고 새 물리 트랜잭션 시작 | 별도 실제 EntityManager·영속성 컨텍스트 사용. 내부가 먼저 commit돼도 외부는 나중에 rollback될 수 있음 |

```text
외부 REQUIRED:       ├──────────── EM A / TX A ────────────┤
내부 REQUIRES_NEW:           ├── EM B / TX B ──┤
                             B commit         A rollback 가능
```

기본 롤백 규칙은 `RuntimeException`과 `Error` 중심이다. checked exception에서도 롤백하려면 `rollbackFor` 등 설정이 필요할 수 있다. 예외를 메서드 안에서 잡아 정상 반환하면 프록시는 실패를 알지 못하므로 그대로 commit할 수 있다. 프록시를 거치지 않는 같은 객체 내부 호출도 새 `@Transactional` 설정이 적용되지 않을 수 있다.

### 혼용 시 조건

MyBatis와 JPA가 같은 물리 트랜잭션·DataSource·커넥션에 참여하는지 확인해야 한다. MyBatis의 SQL 실행은 JPA 영속성 컨텍스트의 관리 Entity를 자동 갱신하지 않는다. flush 시점과 MyBatis 실행 순서도 결과에 영향을 준다.

Spring 관리 `SqlSessionTemplate`과 JPA가 같은 DataSource 및 호환되는 트랜잭션 설정을 사용하면 같은 DB 트랜잭션에 참여하도록 구성할 수 있다. **같은 서비스 메서드에서 호출했다는 이유만으로 같은 트랜잭션이라고 단정하지 않는다.** 트랜잭션 매니저, DataSource, 실제 커넥션을 확인한다.

같은 트랜잭션 안에서 실행되더라도 상태 저장소는 다르다. MyBatis는 SQL을 직접 실행하고, JPA는 영속성 컨텍스트의 Entity를 추적한다. MyBatis가 같은 행을 수정해도 이미 로딩한 JPA Entity는 자동 갱신되지 않는다. JPA의 미반영 변경이 있다면 MyBatis 호출 전 `flush()`가 필요한지, MyBatis 변경 후에는 `refresh()`나 재조회가 필요한지 **순서별로** 판단해야 한다.

## 이력서·포트폴리오 사례 연결

재고 수량 갱신과 이력 저장이 같은 원자적 경계에 있었는지, MyBatis 갱신이 JPA 캐시와 언제 어긋났는지 코드·SQL 로그로 확인한다.

이 사례는 **서로 다른 트랜잭션의 순서**와 **한 트랜잭션 안의 관리 Entity 상태**를 함께 봐야 한다.

```mermaid
sequenceDiagram
 participant T1 as Tx1 · JPA 패킹존 스캔
 participant PC as Tx1 영속성 컨텍스트
 participant T2 as Tx2 · MyBatis
 participant DB as 재고 DB 행
 T1->>DB: EntityGraph 조회
 DB-->>PC: 수량 100 관리
 T2->>DB: 행 락 → 수량 90 변경 → commit
 T1->>DB: 행 락 획득
 Note over PC: 수량 100이 자동으로 90이 되지 않음
 T1->>DB: refresh()로 수량 90 재조회
 DB-->>PC: 최신 수량 반영
 T1->>DB: 최신 수량 기준 변경 → commit
```

비관적 락은 유지하고 락 직후 `refresh()`한 이유를 설명한다. 수량 변경과 이력 저장의 원자적 범위, 실패 시 롤백, 커넥션 사용 방식은 실제 코드·설정으로 검증할 항목이다.
