# 사례 컨텍스트와 사실 경계

## 재고 정합성

- MyBatis 기존 API와 JPA 신규 API가 같은 재고를 변경했다.
- JPA는 락 획득 전 재고 Entity를 영속성 컨텍스트에 적재했다.  
  다른 트랜잭션이 DB를 변경한 뒤 비관적 락을 획득해도 이미 적재된 Entity의 수량은 자동 갱신되지 않았다.
- 선택: 재고 ID 오름차순으로 한 번씩 락을 획득한 뒤 `EntityManager.refresh()`를 호출했다.  
  이력은 JdbcTemplate으로 일괄 INSERT했다.  
  대량 UPDATE·clear 전 flush로 변경 유실을 방지했다고 기재되어 있다.
- 기재 성과: 추가 불일치는 6개월간 관측되지 않았다.  
  Lock Timeout은 주 약 7건→0건이었다.  
  평균 DB 쿼리는 2,571→34였으며 p95는 2,733ms→141ms였다.
- 2026-11-18 본인 추가 설명: 패킹존 스캔 API에서 EntityGraph 선조회, 비관적 락 획득 직후 `refresh()` 적용.  
  변경 히스토리로 대상 재고를 찾아 재고조정 기능으로 복구하고 6개월간 주간 확인.  
  4개 컬럼이 모두 바뀌면 안 되고 2개 또는 3개만 바뀌어야 한다는 규칙을 활용했다고 설명했으나 상세 컬럼·판정식은 미확인.  
  p95는 같은 API의 배포 전 7일과 후 7일 비교이며 669개가량의 상품을 포함한 큰 요청을 기준으로 설명함.  
  전후 요청별 상품 수·부하 분포의 동일성은 미확인.
- 주의: “미관측”은 정합성을 수학적으로 증명한다는 뜻이 아니다.  
  대사 범위와 탐지 민감도 확인 전에는 “0건 보장”으로 표현하지 않는다.

## API 성능 및 SLO

- 15개 API에서 N+1, 일괄 UPDATE, 인덱스, 조인, 외부 호출, 연결 점유, 병렬 조회·캐시를 개선했다고 기재되어 있다.
- 2026년 10월 기준 WMS와 WMS·OMS 연동 모듈의 가용성·지연·실질 성공률 SLO 6개를 등록했다.  
  목표는 모두 99.9%이며 전후 7일을 비교했다.
- WMS 지연 98.56→98.89%, 실질 성공률 98.87→99.91%. 연동 모듈 실질 성공률은 99.73→99.56%로 악화됐다.  
  그 원인과 후속 대응은 원자료 확인 필요.
- 2xx로 반환된 처리 실패를 재분류했으므로 지표 변화에는 측정 기준 변화가 포함될 수 있다.

## 주문·설계·협업

- 주문 중복 수집과 송장 중복 발행에 애플리케이션 멱등키와 DB unique 제약을 적용했다고 기재되어 있다.
- 송장 출력은 Graphics2D→ZPL 변환, Factory Method·Strategy 설계로 1,000장 약 50초→8초.
- CLASS101 회원 도메인은 Node.js·MongoDB에서 Spring Boot·MySQL 독립 서비스로 분리하며 외부 token 기반 Dual Write·스크립트·전수 검증을 사용했다.
- PLE로 기획 리뷰, Design Document/RFC/ADR, QA 분담, Jira/GitHub 자동화, AI 공통 가이드를 도입했다.
