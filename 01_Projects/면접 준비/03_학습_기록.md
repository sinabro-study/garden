### 2026-11-19 / 재고 정합성 02: Spring 트랜잭션

- Level 1. ACID의 큰 틀과 선언적 트랜잭션을 설명했다.  
  일관성은 커밋 결과가 정의된 제약을 만족한다는 뜻이다.  
  격리 수준에 따라 동시 실행 중 보이는 데이터와 허용되는 현상이 달라진다.
- Level 2. 시작·정상 종료·롤백 흐름을 설명했다.  
  새 물리 트랜잭션에서 begin이 일어난다.  
  서비스 프록시는 종료 시 트랜잭션 매니저에 commit을 요청하고 JPA는 필요한 변경을 flush한다.
- Level 3. 내부 호출에서는 호출된 메서드의 설정이 적용되지 않는다고 설명했다.  
  이미 열린 트랜잭션은 계속 사용한다.  
  checked exception은 기본 규칙에서 롤백 대상에 포함되지 않으며 `rollbackFor` 등으로 지정할 수 있다.
- Level 4. `REQUIRES_NEW`의 독립적인 커밋·롤백을 설명했다.  
  내부 예외가 바깥 경계까지 전달되면 바깥 트랜잭션도 자체 롤백 규칙에 따라 롤백될 수 있다.  
  외부 자원을 유지한 채 별도 커넥션을 얻는 비용도 설명한다.
- Level 5. 두 API의 실행 순서를 `Thread.sleep()`으로 조절해 재현했다고 설명했다.  
  Tx2 커밋 이후 Tx1이 락을 획득하는 순서와 Tx1이 오래된 값을 바탕으로 실제로 수량을 덮어쓰는 UPDATE를 실행한 조건을 설명해야 한다.  
  기존 값 10을 읽기만 했다면 변경 감지만으로 수량 10을 저장하지 않는다.
- 검증 범위.  
  동시 실행 재현과 롤백 검증을 구분한다.  
  별도 트랜잭션을 쓰면 이미 커밋된 상대 트랜잭션은 유지된다.  
  실패를 주입해 재고 수량과 이력 저장이 함께 롤백되는지 검증했는지는 미확인이다.  
  이미 저장된 불일치는 앞 단원에서 정리한 이력 기반 재고조정으로 복구했다.
- 재응답.  
  격리 수준에 따라 동시 변경의 가시성이 달라진다고 정정했다.  
  Tx1은 락 획득 후 최종 재고 필드 대신 다른 필드를 수정했다.  
  실제 Hibernate UPDATE가 최종 재고 컬럼도 포함했는지는 SQL로 확인할 부분이다.  
  `refresh()` 적용 후 최종 재고는 재고 차감 이력과 대조했다는 설명으로 사례 검증은 통과로 기록했다.
- Level 4 보완.  
  `REQUIRES_NEW`는 바깥 트랜잭션을 중단하고 내부에 별도 물리 트랜잭션을 시작한다.  
  내부에서 DB 작업을 하면 별도 커넥션이 필요하다.  
  내부 롤백 상태는 독립적이다.  
  예외가 바깥 메서드까지 나가면 바깥 트랜잭션은 자체 규칙으로 롤백을 판단한다.

### 2026-11-18 / 재고 정합성 01: JPA

- 무자료 답변: Level 1~5 답변을 채팅에서 제출.  
  패킹존 스캔 API의 EntityGraph 선조회, 락 후 `refresh()`, 이력 기반 수량 복구와 6개월 관측을 본인 경험으로 설명함.
- Level별 점수(정확성/사례 연결/반문 대응): L1 2/2/1, L2 2/2/1, L3 2/2/1, L4 2/1/1, L5 2/2/1. 본인 추가 설명을 반영한 임시 점수이며 L1~3·L5 통과, L4 대안 비교 보강.
- 잘 설명한 점: 영속성 컨텍스트와 1차 캐시 역할, flush/refresh/commit 차이, 선조회→다른 트랜잭션 변경→락 후 이전 Entity 사용 시퀀스를 연결함.
- 수정할 표현: 문제 원인은 'optimistic lock'이 아니라 JPA 관리 Entity의 오래된 상태와 MyBatis 변경의 불일치.  
  낙관적 락은 검토 가능한 대안이지만 두 경로의 버전 계약·충돌 처리·재시도가 필요함.
- 실제 사례 추가: 패킹존 스캔 API에서 EntityGraph로 재고 Entity가 먼저 로딩됨.  
  이후 ID로 행 락을 잡고 바로 `refresh()`한 뒤 변경.  
  수량 복구는 이력을 바탕으로 대상 재고를 찾고 재고조정 기능을 사용함.  
  6개월 관측도 이력 기반으로 수행했다고 회상함.
- 성과 측정 정정: 같은 API의 배포 전 7일과 후 7일 p95 2,733→141ms 비교.  
  669개가량의 상품을 포함한 큰 요청을 기준으로 설명했으나 각 기간의 요청별 상품 수 분포·표본·부하가 동일한지는 미확인.  
  동일 API의 운영 전후 관측값으로 말하되 통제 실험처럼 표현하지 않음.
- 관측 근거 보강: 변경 히스토리를 주간 단위로 확인.  
  4개 컬럼이 동시에 변경되면 안 되고 2개 또는 3개만 변경돼야 한다는 규칙을 사용했다고 설명.  
  정확한 컬럼명·허용 조합·탐지 쿼리·실행 기록은 미확인.
- 면접 답변 수준: 컬럼명 네 개를 나열할 필요는 없다.  
  “재고 변경 이력에서 정상 변경 패턴을 벗어난 건을 매주 확인했다”로 설명하고 추가 질문 때 판정 방식과 한계를 말한다.
- 추가 질문 대비: 정확한 컬럼명·탐지 쿼리, EntityGraph의 코드 위치, 락 SQL과 Tx2 commit 순서, p95의 요청별 상품 수 분포·표본 수는 개인 확인 자료로만 보강한다.
- 다음 복습: L4에서 최초 락 조회/낙관적 락/원자적 UPDATE/전면 전환 비교.  
  L5에서 이력 대사 방법과 p95 비교 한계를 정직하게 2분 답변으로 정리.
