최종 갱신: 2026-11-11 (Asia/Seoul)

이 문서는 다른 컴퓨터나 새 대화에서 기존 수업을 이어가기 위한 인계 문서다. 현재 학습 상태는 `학습진도.md`, 전체 일정은 `학습계획.md`와 함께 확인한다. 기록이 달라지면 최신 날짜의 실제 답변·평가 기록을 우선하고, 확인되지 않은 완료나 점수를 추정하지 않는다.

## 4. 반드시 지킬 수업 방식

1. 먼저 해당 수업 자료 파일에 개념 설명, 예제, 확인 문제를 준비한다.
2. 자료 링크를 제공하고, 자료 범위 안에서 설명한다.
3. 사용자가 직접 답하도록 문제를 제시한다. 미응답 문제의 정답은 미리 공개하지 않는다.
4. 답변을 채점하되, 결론이 맞는 것과 이유가 정확한 것을 구분한다. 이유가 모호하면 짧게 교정한다.
5. 답변을 받은 뒤 자료에 해설을 반영하고 `학습진도.md`를 갱신한다.
6. 수업을 마치거나 다음 행동이 바뀌면 이 문서의 현재 상태도 함께 갱신한다.

사용자가 “수업 자료에 없는데”라고 지적한 이력이 있다. 새 개념을 채팅에서 먼저 가르치거나 자료에 없는 문제를 내지 않는다. 필요한 내용은 자료에 먼저 추가한다.

수업은 설명 → 예제 → 설계/확인 문제 → 채점·해설 → 복습으로 진행한다. 사용자는 “ㅇㅇ 다음”처럼 짧게 다음 단계 진행을 요청할 수 있다. 그때는 다음 자료를 준비하고 바로 수업을 진행한다.

실제 AWS 실습 전에는 사용 가능한 계정과 허용 비용을 확인하고 생성할 리소스, 예상 비용, 삭제 절차를 안내한다. 파일 작성 요청을 AWS 계정 조작의 승인으로 해석하지 않는다.

### 이미 보충 설명한 사항

- Multi-AZ는 AZ 단위 장애에 대비하는 구성이다. 리전 전체 장애 대비는 별도로 설계한다.
- 단일 AZ 장애가 모든 AWS 서비스의 중단을 뜻하지는 않는다. 해당 AZ에 의존하는 구성요소가 영향을 받을 수 있다.
- EC2 게스트 운영체제 패치는 고객 책임이다. 모든 AWS 서비스의 기반 OS를 고객이 패치하는 것은 아니다.
- S3의 기반 OS는 AWS가 관리한다. 누가 회사 파일에 접근할지 결정하고 설정하는 일은 고객 책임이다.
- 서버 대수 확대, 수요에 따른 확대·축소, 장애 격리는 관련이 있지만 구분하여 판단한다.

### Aurora 후속 질문 보충 — 2026-11-06

사용자가 Replica lag와 Phantom Read는 다르겠다고 질문했다. 구분이 맞다고 설명하고 42번 자료에 추가했다.
Replica lag는 인스턴스 간 반영 지연이고 Phantom Read는 같은 트랜잭션의 조건 재조회에서 다른 트랜잭션 COMMIT으로 행 집합이 달라지는 현상이다.
복제 없는 단일 Writer에서도 가능하며 PostgreSQL Read Committed와 Repeatable Read 차이를 공식 문서로 확인해 보충했다.
이 Phantom Read 보충 자체에는 새 평가나 반복 질문이 없다. 이후 DynamoDB 43번 자료를 제공했고 현재 위치는 5절을 따른다.

사용자가 DynamoDB도 Aurora처럼 6개로 구성되는지 질문했다.
44번 자료에 현재 DynamoDB 공식 문서의 3개 AZ 복제 및 Amazon Science 2022 공개 설계의 파티션당 3개 사본을 구분해 추가했다.
Aurora PostgreSQL/MySQL은 3개 AZ의 공유 스토리지 6개 노드/사본이며 DB 인스턴스 수와 다르다고 설명했다.
DynamoDB 테이블 전체 디스크 수가 3개라는 뜻이나 사용자가 내부 사본 수를 설정한다는 뜻은 아니다.
추가 평가·진도 변경 없이 다음은 조건부 쓰기·트랜잭션 기초 그대로다.


### 물리 디스크·파티션·AZ 구분 질문 — 2026-11-06

사용자가 물리 디스크 하나를 파티션으로 나눠 AZ에 배치할 수 있는지 질문했다.
44번에 논리적 테이블 분할과 각 파티션의 다중 AZ 데이터 복제는 별개이며 물리 디스크 하나가 AZ들을 걸치는 것이 아니라고 설명했다.
파티션 P의 데이터 사본은 각 AZ의 별도 저장 자원에 있고 파티션과 물리 SSD가 1:1이라는 의미도 아니라고 구분했다.
추가 평가·진도 변경은 없다.


### DynamoDB ring 구조 후속 질문 — 2026-11-06

사용자가 파티션별 리더 설명 후 DynamoDB가 ring 구조인지 질문했다.
45번에 2007 Dynamo의 consistent-hashing ring과 현재 DynamoDB를 동일시하지 말고 해시 기반 파티션 배치와 복제 그룹 리더는 별도 설계 축이라고 설명 추가했다.
현재 공개 문서의 내부 해시→파티션 및 공개 설계의 라우터·메타데이터·리더를 근거로 설명하며 내부에 ring이 전혀 없다고 단정하지 않는다.
새 평가나 진도 변경은 없으며 다음은 ElastiCache 캐시·공유 세션 기초다.


### 파티션 개수 후속 질문 — 2026-11-06

사용자가 한 파티션 복제 그룹을 이해한 뒤 전체 파티션 수를 질문했다.
45번에 데이터 크기·처리량에 따라 서비스가 자동 관리해 고정 수가 아니라는 점을 추가했다.
각 AZ에 사본이 있는 것이며 AZ 자체가 복제 그룹 노드가 아니고 AZ-A가 항상 리더도 아니라는 점을 명확히 했다.
파티션마다 리더가 다를 수 있고 서로 다른 파티션의 데이터 분할과 같은 파티션의 사본 복제를 구분했다.
새 평가·진도 변경 없이 다음은 ElastiCache 기초 그대로다.
