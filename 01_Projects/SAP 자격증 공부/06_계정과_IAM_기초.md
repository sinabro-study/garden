# 2주차 첫 수업: 계정과 IAM 기초

예상 30~40분 · AWS 계정 조작 및 유료 리소스 생성 없음 · 확인 문제 평가 완료 3/3

## 목표

누가 AWS에 접근하는지 확인하는 일(인증)과 무엇을 허용할지 결정하는 일(인가)을 구분한다.
루트 사용자·MFA·IAM 역할·최소 권한의 의미를 설명한다.

## 1. AWS 계정과 루트 사용자

AWS 계정은 AWS 리소스와 접근 권한과 비용 등을 관리하는 기본 단위다.
루트 사용자(root user)는 계정의 최상위 권한을 가진 신원이다.
일상적인 개발·운영 작업에 루트 사용자를 사용하지 않고 루트가 필요한 작업에 한정한다.

예: 문서 하나를 읽는 직원에게 건물 전체의 만능 열쇠를 주지 않듯 평소 작업에 루트 권한을 사용하지 않는다.

## 2. IAM과 인증·인가

IAM(Identity and Access Management)은 AWS 리소스에 누가 접근하고 무엇을 할 수 있는지 관리하는 서비스다.

- 인증(Authentication): “누구인지” 확인한다.
  로그인 과정이 대표적인 예다.
- 인가(Authorization): “어떤 작업을 허용할지” 판단한다.
  S3 파일 읽기 허용 여부가 예다.

예: 직원이 로그인에 성공해도 파일 삭제 권한까지 자동으로 생기는 것은 아니다.

## 3. MFA

MFA(Multi-Factor Authentication · 다중 요소 인증)는 서로 다른 종류의 인증 요소를 조합해 신원을 확인하는 방식이다.
비밀번호와 인증 앱의 일회용 코드를 함께 사용하는 것이 한 예다.
일회용 코드만이 MFA의 전부는 아니다.

### 인증 요소의 기본 분류

- 지식 요소: 내가 아는 것. 비밀번호나 PIN이 예다.
- 소유 요소: 내가 가진 것. 휴대전화나 물리 보안 키가 예다.
- 생체 요소: 나의 신체적 특성. 지문이나 얼굴이 예다.

비밀번호 두 개를 쓰는 것만으로는 서로 다른 인증 요소를 조합한 것이 아니다.
PIN이나 생체 인증은 패스키를 사용할 기기의 잠금을 해제하는 데 쓰일 수 있다.

### FIDO와 TOTP의 뜻

FIDO(Fast Identity Online)는 공개 키 암호 기술을 사용하는 인증 표준들의 이름이다.
패스키와 FIDO 보안 키가 이 표준을 사용한다.
등록할 때 서비스에 공개 키를 등록하고 인증할 때는 비밀 키로 서비스의 요청에 대한 서명을 만든다.
서비스는 공개 키로 그 서명을 확인한다.
비밀 키는 서명을 만드는 열쇠이고 공개 키는 그 서명이 맞는지 확인하는 열쇠다.
비밀 키 자체를 로그인할 서비스에 보내지 않는다.

예: AWS 로그인 중 Touch ID로 패스키 사용을 승인하면 기기가 인증 요청에 서명한다.
숫자 코드를 사람이 옮겨 입력하지 않는다.
FIDO 인증은 등록된 서비스에 연결되므로 가짜 사이트로 인증을 유도하는 피싱에 강하다.

TOTP(Time-Based One-Time Password)는 시간 기반 일회용 비밀번호를 만드는 알고리즘이다.
인증 앱이나 전용 토큰과 서버가 공유하는 비밀값에 현재 시간 구간을 반영해 코드를 계산한다.
흔히 30초마다 바뀌는 6자리 숫자 코드로 사용한다.
코드 생성 자체에는 인터넷 연결이 필요하지 않지만 기기 시간이 맞아야 한다.

예: 인증 앱에 표시된 6자리 숫자를 AWS 로그인 화면에 입력한다.
앱이 숫자를 서버에서 문자로 받아 오는 것은 아니다.
시간 구간이 지나면 코드가 바뀌지만 가짜 사이트에 현재 코드를 입력하면 공격자가 이를 이용할 수 있다.

| 구분 | FIDO 방식 | TOTP 방식 |
|---|---|---|
| 인증 증명 | 공개 키로 확인하는 전자 서명 | 공유 비밀값과 시간으로 계산한 코드 |
| 사용자 동작 | 패스키 사용 승인 또는 보안 키 조작 | 표시된 숫자 코드 입력 |
| 예 | 패스키·FIDO 보안 키 | 인증 앱·하드웨어 TOTP 토큰 |
| 피싱 대응 | 서비스에 연결된 인증으로 피싱에 강함 | 유효한 코드를 가짜 사이트에 입력할 위험이 있음 |

참고: [FIDO 용어와 표준](https://docs.yubico.com/yesdk/users-manual/application-fido2/fido2-overview.html)과 [TOTP 표준 RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238).

### AWS 루트 사용자와 IAM 사용자가 지원하는 MFA 종류

AWS 공식 분류는 패스키·보안 키와 가상 인증 앱 및 하드웨어 TOTP 토큰의 세 가지다.
아래에서는 패스키와 보안 키를 나눠 비교한다.

| 방식 | 사용하는 방법 | 예 | 일회용 코드 직접 입력 |
|---|---|---|---|
| 동기화 패스키 | 자격 증명 관리자에 저장된 패스키를 기기 인증 후 사용한다 | Apple·Google 등의 자격 증명 관리자에 저장한 패스키 | 필요 없음 |
| 물리 보안 키 | 별도 FIDO 보안 장치를 연결하거나 접촉해 인증한다 | YubiKey 같은 보안 키 | 필요 없음 |
| 가상 인증 앱 | 앱이 생성한 시간 기반 일회용 코드인 TOTP를 입력한다 | 휴대전화의 TOTP 인증 앱 | 필요 |
| 하드웨어 TOTP 토큰 | 전용 장치에 표시된 시간 기반 일회용 코드를 입력한다 | AWS와 호환되는 OTP 토큰·표시 카드 | 필요 |

패스키는 비밀번호 대신 공개 키 암호 기술로 인증하는 자격 증명이다.
AWS의 MFA에서는 추가 인증 수단으로 사용할 수 있다.
Touch ID나 Face ID는 이때 패스키 사용을 승인하는 데 활용할 수 있다.
AWS에 지문이나 얼굴을 직접 보내서 대조한다는 뜻은 아니다.

보안 키와 하드웨어 TOTP 토큰은 모두 물리 장치지만 인증 방식은 다르다.
보안 키는 FIDO 방식으로 인증하고 하드웨어 TOTP 토큰은 표시된 숫자를 사람이 입력한다.
AWS는 피싱에 강한 패스키나 보안 키 사용을 권장한다.

SMS 문자 기반 MFA는 신규 활성화를 지원하지 않는다.
IAM Identity Center나 외부 회사 로그인 시스템의 MFA 지원 범위는 별도로 확인한다.

MFA는 인증을 강화한다.
읽기 권한만 있는 사람이 MFA 인증을 했다고 삭제 권한을 얻는 것은 아니다.

예: 맥에서 패스키로 MFA 인증을 할 때 Touch ID로 사용을 승인할 수 있다.
숫자 코드를 직접 입력하지 않아도 MFA를 수행할 수 있다.

참고: [AWS IAM MFA 종류](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_mfa.html)와 [패스키·보안 키 등록](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_mfa_enable_fido.html).
확인: 2026-10-31.

## 4. 정책과 최소 권한

정책(Policy)은 어떤 작업을 어떤 리소스에 허용(Access)하거나 거부(Deny)할지 표현한 규칙이다.
이번에는 세부 문법보다 범위를 이해한다.

최소 권한(Least privilege)은 업무에 필요한 작업과 리소스 범위만 허용하는 원칙이다.

예: 앱이 특정 S3 버킷의 상품 이미지를 읽기만 한다면 그 범위의 읽기 권한을 부여한다.
계정 전체 관리자 권한이나 파일 삭제 권한까지 줄 필요는 없다.
버킷은 S3에서 파일 같은 객체를 담는 저장 공간이다.

## 5. IAM 역할과 임시 자격 증명

IAM 역할(Role)은 허용된 사람·애플리케이션·서비스가 맡아 사용할 수 있는 AWS 신원이다.
“누가 역할을 맡을 수 있는가”와 “그 역할로 무엇을 할 수 있는가”를 설정한다.

역할을 맡으면 임시 자격 증명을 사용한다.
자격 증명은 AWS 요청에서 신원을 증명하는 정보다.
임시 자격 증명은 유효 기간이 있다.
EC2에서 실행하는 앱에는 적절한 IAM 역할을 연결해 임시 자격 증명을 사용하도록 구성할 수 있다.
앱 코드에 장기 액세스 키를 넣어 배포하는 방식을 피한다.

예: EC2 앱에 상품 이미지 읽기 역할을 연결한다.
앱은 AWS SDK를 통해 제공되는 임시 자격 증명을 사용해 S3를 읽는다.
SDK는 코드에서 AWS 기능을 호출하도록 돕는 개발 도구 모음이다.
EC2 역할의 임시 자격 증명 갱신도 SDK의 지원을 활용할 수 있다.

사람의 일상적인 AWS 접근에는 IAM Identity Center 같은 중앙 접근 관리와 임시 자격 증명 사용을 우선 고려한다.
IAM 사용자는 역할과 다른 신원이며 장기 자격 증명을 가질 수 있다.
모든 직원에게 장기 액세스 키를 만들게 하는 것이 기본 권장 방식은 아니다.
구체적인 사용자·역할 비교는 다음 수업에서 다룬다.

## 6. 예제: 상품 이미지를 읽는 앱

EC2 앱은 특정 S3 버킷의 상품 이미지만 읽는다.

1. 앱이 맡을 수 있는 IAM 역할을 준비한다.
2. 역할에는 필요한 상품 이미지 읽기 범위만 허용한다.
3. EC2에 역할을 연결하고 앱이 임시 자격 증명을 사용하도록 구성한다.
4. EC2 게스트 OS 패치는 여전히 고객 관리 범위다.
   역할 사용은 패치 책임을 AWS로 넘기지 않는다.

이번에는 설계만 설명한다.
실제 역할 생성이나 계정 설정 변경은 진행하지 않는다.

   적절한가?
   이유는?
2. S3 파일 읽기만 허용된 직원이 MFA로 로그인했다.
   이제 파일 삭제도 가능하다고 볼 수 있는가?
   인증과 인가를 구분해 설명하자.
3. EC2 앱이 특정 S3 버킷의 이미지를 읽기만 한다.
   코드에 관리자 장기 액세스 키를 넣는 방법과 필요한 읽기 권한의 IAM 역할을 EC2에 연결해 임시 자격 증명을 쓰는 방법 중 무엇을 선택하겠는가?
   권한 범위도 함께 설명하자.

## 2026-10-31 확인 문제 평가 — 3/3

1. 정답.
   일상적인 개발 작업에 루트 사용자를 사용하는 것은 적절하지 않다.
   필요한 작업만 허용하는 최소 권한 원칙을 근거로 정확히 판단했다.
   루트 사용자는 루트 권한이 필요한 작업에 한정한다.
2. 정답.
   MFA 로그인은 인증을 강화하는 행위이고 파일 삭제 가능 여부는 인가의 문제다.
   읽기 권한만 있으면 MFA 인증을 해도 삭제할 수 없다고 정확히 설명했다.
3. 정답.
   EC2에 필요한 읽기 권한만 있는 IAM 역할을 연결하는 방법을 선택했다.
   관리자 장기 액세스 키를 코드에 넣을 때의 탈취 위험과 임시 자격 증명 사용의 이점을 설명했다.
   용어는 “임시 자격 권한”보다 “임시 자격 증명”이 정확하다.
   임시 자격 증명도 탈취되면 유효 기간 동안 허용된 권한으로 사용될 수 있다.
   따라서 임시 자격 증명을 사용하면서 권한도 필요한 읽기 범위로 제한해야 한다.
   장기 비밀값을 코드에 넣지 않는 것과 만료 기간을 두는 것 및 권한 범위를 줄이는 것이 함께 위험을 낮춘다.

새 수업 자료를 먼저 준비한 뒤 설명과 확인 문제를 진행한다.
