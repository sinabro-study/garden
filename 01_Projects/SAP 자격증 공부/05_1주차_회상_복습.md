# 1주차 다섯 번째 수업: 회상 복습

예상 10~15분 · 자료를 덮고 자기 말로 설명하기 · 핵심 이해 확인 완료

## 현재까지 확인한 내용

종합 확인은 5/5로 통과했다. 이번에는 선택지 없이 핵심 원리를 설명하며 첫 주를 마무리한다. 새로운 AWS 서비스나 실제 리소스 생성은 다루지 않는다. 2026-10-31 답변을 확인했고, 종합 확인 5/5 및 회상 복습을 근거로 1주차 완료를 기록했다.

## 보완 설명과 예제

EC2 게스트 OS 패치는 OS를 누가 설치했는지와 관계없이 고객의 관리 범위에 속한다. 예를 들어 AWS가 제공한 이미지로 EC2를 시작해도 이후 게스트 OS 보안 패치는 고객 책임이다.

연결 자동 복구는 드라이버·버전·DB 배포 방식의 지원 범위에 따라 다르다. 자동 재연결 기능이 있어도 장애 감지와 DB 전환, 연결 복구에 시간이 걸리므로 주문 저장이 일시적으로 실패할 수 있다. 기존 수업의 RDS Multi-AZ DB 인스턴스와 Aurora·RDS Multi-AZ DB 클러스터를 구분한다.

## 회상 문제 — 해설은 답변 후 추가

한 리전에 ALB, 두 AZ에 나눈 EC2 웹 서버, RDS for MySQL Multi-AZ DB 인스턴스가 있는 쇼핑몰을 가정한다. 자료를 덮고 아래 세 가지를 짧게 설명하자.

1. AZ 하나에 장애가 났을 때 웹 요청과 DB 연결이 복구되는 흐름을 설명하고, 이 구성이 대비하지 못하는 더 큰 장애 범위도 말해보자.
2. AWS 제공 이미지로 EC2를 만들었다. 게스트 OS 보안 패치는 누구의 책임이며, 그 이유는 무엇인가?
3. 행사 수요에 맞춰 서버 대수를 늘렸다가 줄이는 것과, 서버를 여러 AZ에 나누는 것은 각각 어떤 문제를 해결하는가?

## 2026-10-31 회상 복습 평가

- 1번: 정상 웹 서버로의 ALB 전달, 대기 DB의 주 DB 승격, 리전 전체 장애 대비의 한계를 설명했다. 핵심 흐름은 맞다. 표현상 헬스 체크가 정상인 대상은 AZ 자체가 아니라 웹 서버다. 이번 답변에서는 재연결을 다시 명시하지 않았지만 직전 종합 확인 5번에서 이미 설명했으므로 이해 확인 근거로 함께 반영한다. 실제 복구에는 새 주 DB로의 연결 복구도 필요하다.
- 2번: 고객 책임과 그 이유를 정확하게 설명했다. 앞서 보완한 EC2 관리 범위를 자기 말로 재확인했다.
- 3번: 탄력성과 AZ 분산의 목적을 구분했다. 표현상 여러 AZ 배치는 AZ 장애 발생 자체를 막는 것이 아니라, 한 AZ 장애에도 다른 AZ에서 서비스를 이어갈 수 있도록 대비하는 것이다. 정상 서버로의 전달, DB 복구, 남은 용량 등의 조건도 함께 갖춰야 한다.

종합 판단: 새로운 종합 확인 5/5 통과 및 회상 복습 핵심 설명 완료. 위 표현을 보완하고 **1주차 완료(1/32)** 처리한다. 세 번째 수업의 과거 부분 정답 기록은 그대로 두고 이후 재확인 결과로 보완한다.
