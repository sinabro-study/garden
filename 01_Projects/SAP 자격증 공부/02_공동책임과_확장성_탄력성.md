예상 45~60분 · AWS 계정과 유료 리소스 불필요

## 학습 목표

- EC2와 S3에서 고객이 맡는 관리 범위를 구분한다.
- 사용량 기반 과금과 비용 감소의 관계를 설명한다.

## 1. 공동 책임 모델 — 앞서 학습한 내용

AWS와 고객은 보안 책임을 나눠 맡는다. AWS는 데이터센터와 기반 인프라를 관리하고, 고객은 자신의 데이터와 접근 권한 등을 관리한다. 고객의 구체적인 책임 범위는 사용하는 서비스에 따라 달라진다.

| 관리 대상 | EC2: 가상 서버 | S3: 관리형 객체 저장소 |
|---|---|---|
| 물리 장비와 데이터센터 | AWS | AWS |
| EC2 인스턴스의 게스트 운영체제 | 고객이 패치·관리 | 해당 없음. S3의 기반 OS는 AWS가 관리 |
| 고객 데이터 접근 권한 설정 | 고객 | 고객 |

S3로 파일 저장 기능을 옮기면 저장소 서버 운영체제를 직접 패치하는 업무를 줄일 수 있다. 회사 문서를 어떤 직원에게 공개할지는 회사가 결정하고 권한을 설정해야 한다. 관리형 서비스에서도 고객의 데이터 관리 책임은 남는다.

### 이미 푼 확인 문제

- 데이터센터 출입 통제: AWS 책임.
- EC2에 설치한 Linux 보안 패치: 고객 책임.
- S3 문서 접근 권한 설정: 고객 책임.
- EC2 파일 저장 서버에서 S3로 옮긴 뒤 저장소 기반 OS 패치: AWS가 관리.
- 옮긴 파일의 직원별 접근 권한: 고객이 결정하고 설정.

## 2. 확장성 — 부하 증가를 처리할 수 있는 능력

확장성(Scalability)은 부하가 증가할 때 자원 용량을 늘려 대응할 수 있는 능력이다.

예: 평소 서버 2대로 운영하는 쇼핑몰이 주문 증가를 처리하기 위해 서버를 10대로 늘릴 수 있다.

## 3. 탄력성 — 수요에 맞춰 늘리고 줄이는 능력

탄력성(Elasticity)은 수요 변화에 맞춰 자원을 늘리고 줄일 수 있는 능력이다. 자동화를 통해 구현하는 경우가 많다.

예: 행사 시작 시 서버를 2대에서 10대로 늘리고, 행사 종료 후 다시 2대로 줄인다. 수요가 낮을 때 불필요한 자원을 줄이면 비용 최적화에 도움이 된다.

확장성과 탄력성은 관련된 개념이다. 시험 문제에서는 부하 증가를 처리하는 능력을 묻는지, 수요 변화에 따라 확대와 축소를 하는 능력을 묻는지 구분한다.

## 4. 용량을 늘리는 두 가지 방법

| 방법 | 의미 | 예 |
|---|---|---|
| 수직 확장(Scale up) | 서버 한 대의 성능을 높인다 | 메모리 8GB에서 32GB로 변경 |
| 수평 확장(Scale out) | 서버 대수를 늘린다 | 서버 2대에서 5대로 증가 |

반대로 서버 성능을 낮추는 것은 수직 축소(Scale down), 서버 대수를 줄이는 것은 수평 축소(Scale in)다.

수평 확장 시 여러 서버가 요청을 나누어 처리하도록 애플리케이션과 요청 분산을 설계해야 한다. 서버 대수만 늘려 모든 문제가 해결되지는 않는다.

## 5. 확장과 AZ 장애 대비의 차이

서버를 2대에서 10대로 늘리면 처리 용량을 늘릴 수 있다. 하지만 10대가 모두 같은 AZ에 있으면 AZ 전체 장애에 함께 영향을 받을 수 있다.

처리 용량을 늘릴 수 있는지와 특정 장애 범위를 견딜 수 있는지는 따로 확인한다. 여러 AZ를 활용한 뒤에도 요청 분산, 데이터 복제, 장애 조치를 함께 설계해야 한다.

## 6. 사용량과 비용

필요한 만큼 자원을 쓰고 줄일 수 있다는 점은 클라우드의 장점이다. 다만 모든 비용이 요청 수와 똑같이 움직이는 것은 아니다. 서버 사용 시간, 저장 용량, 데이터 전송량, 약정 등 서비스별 과금 요소가 있다.

서버 대수를 줄여도 남아 있는 디스크나 데이터 저장 비용 등이 발생할 수 있다. 정확한 금액과 조건은 실제 실습 전에 해당 서비스의 최신 요금을 확인한다.

## 7. 확인 문제 — 풀이 완료 (3/3)

아래는 학습용 자체 제작 문제다. 번호와 판단 이유를 함께 답한다. 정답은 제출 후 해설한다.

1. 서버 한 대의 메모리를 8GB에서 32GB로 바꾸면 수직 확장일까, 수평 확장일까?
2. 접속자가 많아지면 서버를 추가하고, 줄어들면 서버를 제거하도록 자동화했다. 어떤 개념을 특히 잘 보여주는가?
3. 서버 대수를 늘려도 모두 같은 AZ에 있다면, AZ 전체 장애에 대비했다고 볼 수 있는가?

## 확인 문제 해설

1. 수직 확장. 서버 한 대의 메모리 용량을 늘린다.
2. 탄력성. 수요에 맞춰 서버를 추가하고 제거한다.
3. 같은 AZ의 서버들은 AZ 장애에 함께 영향을 받을 수 있다. 여러 AZ에 분산하고 요청 분산·데이터 복제·장애 조치를 함께 설계해야 한다. Multi-AZ만으로 리전 전체 장애까지 대비하지는 않는다. 단일 AZ 서버 장애가 모든 AWS 서비스의 중단을 의미하지도 않는다.
