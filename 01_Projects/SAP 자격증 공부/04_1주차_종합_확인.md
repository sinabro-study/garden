## 설명과 예제: 앞선 수업 보완

헬스 체크 비정상은 정해 둔 정상 기준을 충족하지 못했다는 뜻이다. 서버 자체 고장뿐 아니라 애플리케이션 오류도 원인일 수 있다.

RDS Multi-AZ DB 인스턴스의 장애 조치는 대기 DB를 새 주 DB로 전환하는 과정이다. 전환에는 시간이 걸리고 기존 DB 연결을 다시 맺어야 하므로 일시적으로 접속이나 주문 저장이 실패할 수 있다.

예: 웹 서버 B는 정상인데 기존 주 DB와 맺었던 연결이 끊겼다. 웹 서버가 정상이라는 사실만으로 주문 저장까지 성공하지는 않는다. 새 주 DB가 준비되고 애플리케이션이 RDS 엔드포인트로 재연결해야 DB를 사용하는 작업을 이어갈 수 있다.

## 확인 문제 — 번호와 이유를 함께 답하기

1. 회사가 한 리전 안의 AZ 세 곳에 서비스를 나눴다. 담당자가 “이제 리전 전체 장애에도 대비했다”고 말했다. 이 판단은 타당한가? AZ와 리전의 관계를 근거로 설명하자.
2. 회사는 EC2에서 웹 애플리케이션을 실행하고 S3에 사내 문서를 보관한다. EC2 게스트 운영체제 보안 패치와 S3 문서의 직원별 접근 권한 설정은 각각 누구의 책임인가?
3. 행사 때 서버를 2대에서 8대로 늘리고, 행사 후 다시 2대로 줄였다. 수직·수평 중 어떤 방식인가? 확대와 축소를 함께 한 동작은 확장성·탄력성 중 어떤 개념을 특히 보여주는가?
4. 웹 서버 8대가 모두 AZ-A에 있다. ALB도 구성했다. “서버가 많고 ALB가 있으므로 AZ-A 전체 장애에도 웹 요청을 계속 처리할 수 있다”는 판단을 평가하고, 웹 계층에서 필요한 개선을 설명하자.
5. RDS for MySQL의 Multi-AZ DB 인스턴스 배포에서 주 DB가 장애를 겪었다. 다른 AZ의 웹 서버는 정상이다. “대기 DB가 즉시 모든 기존 연결을 이어받으므로 주문 저장은 한 번도 실패하지 않는다”는 설명을 평가하자. DB 전환과 애플리케이션 연결을 함께 설명하자.

## 2026-10-31 평가와 해설 — 5/5

1. **정답.** AZ는 리전 내부의 장애 격리 영역이며 같은 리전의 여러 AZ에 배치해도 리전 전체 장애 대비가 되지는 않는다. 판단과 이유 모두 정확하다.
2. **정답, 이유 표현 보완.** 두 작업 모두 고객 책임이다. 다만 EC2 게스트 OS 패치가 고객 책임인 이유는 고객이 OS를 직접 설치했기 때문이 아니라 EC2의 서비스 책임 범위에서 게스트 OS 관리를 고객이 맡기 때문이다. AWS 제공 이미지로 시작해도 이 책임은 고객에게 있다. S3 문서의 직원별 접근 권한도 고객이 결정하고 설정한다.
3. **정답.** 서버 대수를 늘리고 줄였으므로 수평 확장·축소이며, 수요에 맞춘 확대와 축소는 탄력성을 특히 보여준다. 부하 증가에 맞춰 2대에서 8대로 늘릴 수 있다는 점은 확장성도 보여준다.
4. **정답.** 모든 웹 서버가 AZ-A에 있으면 AZ-A 전체 장애 시 ALB가 요청을 보낼 정상 웹 서버가 남지 않을 수 있다. 웹 서버를 여러 AZ에 분산하고 정상 서버로 요청을 전달하도록 구성해야 한다. 남은 서버의 처리 용량도 확인한다.
5. **정답.** 대기 DB의 주 DB 승격 및 연결 복구에는 시간이 걸리며 일시적인 접속 실패가 발생할 수 있다. 드라이버를 사용해도 무중단이 보장되지는 않는다는 점을 정확히 설명했다. 단, 앞서 보충한 대로 AWS Advanced JDBC Wrapper의 자동 Failover 기능은 지원되는 배포 방식에서 적용되며 이번 RDS Multi-AZ DB 인스턴스 배포에 무조건 적용된다고 일반화하지 않는다. 중단 구간은 승격 순간만이 아니라 장애 감지·전환·재연결 과정에 걸칠 수 있다.
