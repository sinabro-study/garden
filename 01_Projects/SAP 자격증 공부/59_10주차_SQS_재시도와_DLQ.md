# 10주차 세 번째 수업 · SQS 재시도와 DLQ

![AWS 공식 SQS 메시지 수명 주기](https://docs.aws.amazon.com/images/AWSSimpleQueueService/latest/SQSDeveloperGuide/images/sqs-message-lifecycle-diagram.png)

그림은 원본 큐에서 메시지를 보내고 받고 삭제하는 흐름을 보여 준다.
이번 수업에서는 워커가 삭제까지 마치지 못했을 때를 살펴본다.

## 일시 실패와 반복 실패

배송 시스템이 잠깐 응답하지 않으면 워커는 작업 완료를 기록하거나 메시지를 삭제하지 않는다.
가시성 제한 시간이 지나면 메시지를 다시 받아 처리할 수 있다.
다음 수신 때 배송 시스템이 복구됐다면 워커가 작업을 마치고 메시지를 삭제한다.

반면 주문 번호가 빠진 메시지는 같은 코드로 다시 처리해도 계속 실패할 수 있다.
**DLQ(Dead-letter queue)**는 이렇게 처리되지 않은 메시지를 따로 모으는 큐다.
원본 큐의 **redrive policy**에 대상 DLQ와 `maxReceiveCount`를 설정한다.
`maxReceiveCount`는 원본 큐에서 메시지를 받을 수 있는 횟수의 한도다.
예를 들어 3이라면 원본 큐에서 최대 3번 받을 수 있고, 삭제 없이 한도를 넘기게 되면 SQS가 DLQ로 옮긴다.
SQS는 워커 로그의 오류 종류 대신 수신 횟수와 삭제 여부를 기준으로 동작한다.

## DLQ에서 복구하기

DLQ에 쌓인 메시지와 워커 로그를 보고 원인을 찾는다.
예를 들어 워커가 유효한 메시지의 새 필드를 읽지 못했다면 코드를 고친 뒤 **DLQ redrive**를 시작해 메시지를 원본 큐로 돌려보낼 수 있다.
메시지 내용 자체가 잘못됐다면 내용을 고치거나 생산자가 정상 메시지를 다시 보내도록 해야 한다.
원본 큐로 돌아온 메시지는 워커가 처리한다.
이전에 처리까지 끝내고 삭제만 못한 메시지도 섞일 수 있으므로 주문 번호로 완료 여부를 확인하는 로직은 여전히 필요하다.

## 확인 문제

배송 워커가 Standard 큐에서 메시지를 직접 받고, 성공한 메시지를 삭제한다.
원본 큐는 DLQ에 연결되어 있고 `maxReceiveCount=3`이다.

**1-1.** 배송 시스템이 잠깐 멈춰 워커가 첫 수신에서 메시지를 삭제하지 못했다. 가시성 제한 시간이 지났고 배송 시스템은 복구됐다. 같은 메시지를 다시 받아 정상 처리할 수 있는가?

**1-2.** 다른 메시지는 워커가 세 번 받아도 처리와 삭제를 못했다. 다음 수신에서 한도를 넘기게 되면 SQS는 이 메시지를 어떻게 하는가? `maxReceiveCount`는 수신 횟수와 워커 오류 로그 건수 중 무엇을 세는가?

**2-1.** DLQ의 메시지는 유효하지만 워커 코드에 버그가 있었다. 코드를 고치면 이미 DLQ에 있는 메시지가 자동으로 원본 큐로 돌아가는가? 원본 큐에서 다시 처리하려면 어떤 작업을 시작해야 하는가?

**2-2.** 원본 큐로 돌아온 메시지 중 하나는 배송 준비까지 끝났지만 삭제에 실패했던 메시지다. 다시 받은 워커는 무엇을 확인하고 어떻게 처리해야 하는가?

## 확인 문제 평가 · 2026-11-09

정답 3개, 부분 정답 1개.

- **1-1 정답.** 첫 수신에서 삭제되지 않았고 가시성 제한 시간이 지났다. 아직 수신 한도에 도달하지 않아 다시 받아 처리할 수 있다.
- **1-2 정답.** 수신 한도를 넘기게 되면 SQS가 DLQ로 옮긴다. `maxReceiveCount`는 수신 횟수 기준이다.
- **2-1 정답.** 코드 수정 후 DLQ redrive를 시작해 원본 큐로 돌려보낸다.
- **2-2 부분 정답.** 메시지 삭제는 맞다. 워커는 주문 번호로 배송 준비 완료 상태를 먼저 확인한다. 이미 완료됐다면 작업을 건너뛰고 메시지를 삭제한다.

**2-2 보완 정답.** 주문 번호로 배송 준비 완료 상태를 확인한다. 이미 완료됐다면 작업을 건너뛰고 메시지만 삭제한다.
