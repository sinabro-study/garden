## 주문 접수와 배송 준비를 분리하기

**SQS**는 메시지를 저장하는 관리형 큐다.
큐에 작업을 보내는 쪽은 생산자(producer)이고 큐에서 메시지를 받아 처리하는 쪽은 소비자(consumer)다.

예를 들어 API Gateway는 `POST /shipments` 요청을 받아 접수 Lambda를 동기 호출한다.
접수 Lambda는 SQS에 주문 번호가 담긴 배송 준비 메시지를 보내고 큐에 저장된 것이 확인되면 HTTP 202에 해당하는 결과를 반환한다.
API Gateway는 이 함수 결과를 기다리지만 실제 배송 준비는 기다리지 않는다.
별도의 워커가 나중에 큐에서 메시지를 받아 배송 준비를 실행한다.
따라서 202는 이 예에서 작업 접수가 완료됐다는 뜻이다.
워커가 잠시 멈춰도 메시지는 보존 기간 내에서 큐에 남아 있고 워커가 복구되면 처리할 수 있다.

## 메시지를 받는 것과 삭제하는 것

이 수업에서는 워커가 SQS API를 직접 호출하는 Standard 큐를 가정한다.
워커가 메시지를 받으면 SQS는 **가시성 제한 시간(visibility timeout)** 동안 해당 메시지를 일시적으로 숨긴다.
처리가 성공하면 워커가 메시지를 삭제한다.
삭제 전에 워커가 멈추면 가시성 제한 시간이 지난 뒤 다른 워커가 다시 받을 수 있다.
가시성 제한 시간은 메시지가 숨겨지는 시간이고 보존 기간은 큐가 메시지를 보관하는 최대 시간이다.
Standard 큐에서는 중복 수신이 가능하므로 배송 준비가 이미 끝난 주문 번호로 다시 요청받아도 같은 작업을 중복 실행하지 않도록 설계한다.

## 확인 문제

**1-1.** 접수 Lambda가 배송 준비 메시지를 SQS에 정상 등록했고 클라이언트가 HTTP 202를 받았다. 이 시점에 완료된 작업은 무엇이고 배송 준비도 끝났다고 볼 수 있는가?

**1-2.** 배송 워커가 일시 중단됐지만 접수 Lambda와 SQS는 정상이다. 새 요청을 계속 접수할 수 있는가? 보존 기간 안에 워커가 복구되면 쌓인 메시지는 어떻게 되는가?

**2-1.** 워커 A가 메시지를 받은 뒤 처리나 삭제를 하지 못하고 멈췄다. 가시성 제한 시간이 지나면 워커 B가 같은 메시지를 받을 수 있는가?

**2-2.** 워커 A는 배송 준비를 끝냈지만 메시지를 삭제하기 직전에 멈췄다. 워커 B가 같은 메시지를 받았다면 배송 준비가 두 번 실행되지 않도록 어떤 값을 기준으로 무엇을 확인해야 하는가?

## 확인 문제 평가 · 2026-11-09

하위 문항 4/4 정답.

- **1-1.** 202 응답 시점에 SQS 등록이 완료됐다. 배송 준비 완료 여부는 이 응답으로 알 수 없다.
- **1-2.** 워커가 멈춰도 접수 Lambda와 SQS가 정상이면 새 요청을 접수할 수 있다. 보존 기간이 지나기 전에 워커가 복구되면 큐에 남은 메시지를 처리한다.
- **2-1.** 삭제 전에 가시성 제한 시간이 지나면 워커 B가 같은 메시지를 받을 수 있다.
- **2-2.** 워커 B는 주문 번호로 공유 저장소의 배송 준비 완료 상태를 확인한다. 이미 완료됐다면 배송 준비를 건너뛰고 받은 메시지를 삭제한다.
